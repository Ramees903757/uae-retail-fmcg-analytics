**SQL Server · Power BI · Power Query · DAX**

A six-page retail analytics portfolio project focused on sales performance, profitability, products, inventory, wastage and customers.

> **Publication draft:** This starter package does not include the final Power BI report, current dashboard screenshots, or the author's locally revised SQL/DAX files. Add and verify those assets before removing this notice.

## Business objective

Bring transaction and operational data into a consistent reporting experience so a retail team can compare store performance, examine product contribution, monitor stock, investigate losses and understand customer purchasing.

The project is a simulated UAE multi-store retail scenario. It is not a production deployment, client engagement, or source of UAE market statistics.

## Report scope

| Page | Main business question | Reporting focus |
|---|---|---|
| Overview | How is the retail network performing? | Revenue, gross profit, margin, transactions, average basket value and monthly trends |
| Stores | How do branches compare with each other and their targets? | Sales, profit, basket value and monthly target comparison |
| Products | Which products and categories contribute to sales and margin? | Category mix, product performance, revenue and unit sales |
| Inventory | Where is stock held and which positions require review? | Month-end stock value, quantities, stock status and store/product detail |
| Wastage | Where are recorded product losses occurring? | Wastage cost, reasons, expiry and store/category comparison |
| Customers | Which identified customers and segments purchase? | Active purchasers, repeat purchasing, loyalty segments and basket metrics |

## Dataset

The source is a **synthetic dataset created for this portfolio project**. Store, supplier, product and customer records are simulated. Financial amounts are in AED; sales cover January–December 2025.

| Dataset component | Reference size |
|---|---:|
| Stores | 8 |
| Products / SKUs | 5,000 |
| Customer master records | 25,000 |
| Sales transactions / bills | 100,000 |
| Sales-line records | 448,094 |
| Monthly inventory snapshot records | 480,000 |

Sales transactions and sales lines have different grains: one bill can contain several product lines. The 25,000 customer master records should not be labelled as 25,000 active purchasers.

## Workflow

```text
CSV source files
      ↓
SQL Server staging tables
      ↓
Data-type conversion, null handling and validation
      ↓
Clean relational tables and business-analysis queries
      ↓
Power BI model, Power Query and DAX
      ↓
Six-page report with sidebar navigation
```

The preparation work covered header-row import issues, numeric/date conversion, legitimate anonymous-customer nulls, record counts, duplicate identifiers and key relationships. Analysis and validation were performed in SQL Server Management Studio before the report was built in Power BI.

## Important analytical choices

**Match the measure to the data grain.** Executive bill-level measures and product-line measures serve different purposes. Product/category visuals need measures whose fact table is reached by the selected product/category filter.

**Treat stock as a point-in-time balance.** A month-end inventory card should reflect the intended snapshot, not the sum of balances across all selected months. One product in one store is a stock position; it is not necessarily a distinct company-wide SKU.

**Respect the target grain.** Targets in this project are at store/month level. The report should not imply that a channel or category has an allocated target unless that allocation has been explicitly defined.

**Preserve valid missing customer IDs.** Anonymous transactions remain part of sales, but cannot be used to identify repeat individuals. Customer master count, active-customer count and transaction count are different metrics.

**Separate findings from explanations.** Differences in margin, stock or basket value warrant investigation; they do not, by themselves, establish why a result occurred or prove a business improvement.

## Reproduction and report access

The final release should contain the actual tested SQL files, DAX definitions, dataset access instructions and the Power BI report or a verified release download link. Do not replace them with this starter package alone.

To rebuild, use a separate development SQL Server database, import the documented CSVs into staging, run the reviewed transformation/validation scripts, and connect Power BI to the clean tables. Configure your own local SQL Server connection; the author's local instance is not a hosted data service.

Record the exact SQL Server engine version/compatibility level and Power BI Desktop version used for the final release in `docs/release-validation.md`. Do not assume all functions from the initial learning materials are supported by every SQL Server version.

A GitHub repository is the source/documentation destination. Add a live report link only after an actual deployment exists and its intended access has been tested.

## Limitations

This dataset is synthetic, not market-calibrated. Generated demand, names, stock positions and losses must not be used as real retail benchmarks. It contains only one year of sales, so no prior-year growth claim is made. Returns are stored separately; a sales measure does not automatically become a return-adjusted measure. Wastage records are not a complete account of all possible shrinkage. No realized sales increase, stock reduction or operational savings is claimed.
